# Требования к доработке API (waste-complex-platform)

**Для:** команда бэкенда  
**Клиент:** десктоп-приложение «Учёт промышленных отходов» (C# / WPF)  
**Текущий API:** `http://178.57.217.79:8080/api/v1`  
**БД:** `waste_complex` (из `/core/health`)  
**OpenAPI:** `http://178.57.217.79:8080/openapi.json`

---

## Цель

Доработать сервер так, чтобы все рабочие данные хранились в БД, а клиент мог реализовать **ролевую матрицу** для четырёх ролей: `operator`, `chief`, `ecologist`, `admin`.

Сейчас клиент уже использует: login, batches, classify, waste-types, reporting (частично). Ниже — что **отсутствует** или работает **неполно**.

---

## Роли и общие правила

| Роль | Код в API |
|------|-----------|
| Оператор склада | `operator` |
| Начальник склада | `chief` |
| Эколог | `ecologist` |
| Администратор | `admin` |

**Обязательно:** проверка роли **на сервере** (не только в клиенте). При нарушении — ответ **403 Forbidden** с текстом `detail`.

## 1. Модуль авторизации и доступа

### Уже есть
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/user` (профиль, с Bearer-токеном)

### Нужно добавить

#### 1.1. Смена пароля (все роли)
```
PATCH /api/v1/auth/user/password
Authorization: Bearer <token>
Body: {
  "current_password": "старый",
  "new_password": "новый"
}
```

#### 1.2. Управление пользователями (только `admin`)

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/v1/admin/users` | Список пользователей (пагинация) |
| POST | `/api/v1/admin/users` | Создать: email, password, full_name, role |
| PATCH | `/api/v1/admin/users/{user_id}` | Изменить role, full_name, is_active |
| DELETE | `/api/v1/admin/users/{user_id}` | Удалить или деактивировать |

**Важно:** существующий `POST /api/v1/auth/register` не должен быть доступен обычным пользователям — только через админский endpoint или с проверкой роли `admin`.

#### 1.3. Тестовые учётные записи

Нужны рабочие аккаунты всех 4 ролей (email/пароль передать команде клиента).

## 2. Модуль регистрации партий

### Уже есть
- `POST /api/v1/accounting/batches` — поля включая `volume_tons`, `source_department`
- `GET /api/v1/accounting/batches`

### Нужно

#### 2.1. Права
- **Создавать партию** — только роль `operator` (остальным 403).

#### 2.2. Объём и единицы измерения (желательно)

Сейчас в API только `volume_tons`. Нужно сохранять, **как ввёл оператор**:

```json
{
  "volume": 150,
  "volume_unit": "kg",
  "volume_tons": 0.15
}
```

`volume_unit` — enum: `t` | `kg` | `m3` | `l` (или русские коды, но единообразно в API).

Поле `volume_tons` оставить обязательным (нормализованное значение для отчётов).

#### 2.3. Цех-источник (опционально)
`GET /api/v1/core/departments` — список цехов для выпадающего списка в клиенте.  
Если не делаете — оператор вводит `source_department` текстом (как сейчас).

## 3. Модуль классификации и контроля

### Уже есть
- `PATCH /api/v1/accounting/batches/{batch_id}/classify`  
  Body (`BatchClassify`): `hazard_class`, `fkko_code`, `classification_note`

### Нужно добавить

#### 3.1. Отклонение классификации
```
PATCH /api/v1/accounting/batches/{batch_id}/reject
Body: {
  "reason": "текст причины"
}
```
Эффект: статус партии `rejected`, причина сохраняется в БД.

**Права:** только `ecologist` и `admin` (начальник **не** может reject).

#### 3.2. Подтверждение / ручная классификация
- `PATCH .../classify` — **только** `ecologist` и `admin`.
- Начальник (`chief`) — **только просмотр** партий со статусом `accepted`, без PATCH classify/reject.

#### 3.3. Список партий на проверке
```
GET /api/v1/accounting/batches?status=accepted
```
Фильтрация на сервере, не в клиенте.

#### 3.4. История изменений классификации
Нужен просмотр истории по партии для `ecologist`, `chief`, `admin`.

Вариант А (предпочтительно) — расширить существующий:
```
GET /api/v1/accounting/operations?batch_id={id}
```
В ответе для записей классификации: `operation_type`, `user_id`, `user_name`, `hazard_class` (было/стало), `notes`, `operation_at`.

Вариант Б — отдельный endpoint:
```
GET /api/v1/accounting/batches/{batch_id}/classification-history
```

## 4. Модуль истории и отчётности

### Уже есть (клиент пока не подключил)
- `GET /api/v1/reporting/dashboard` — KPI
- `GET /api/v1/reporting/summary/by-hazard` — сводка по классам опасности

### Нужно

#### 4.1. Фильтры для списка партий
```
GET /api/v1/accounting/batches?date_from=2026-01-01&date_to=2026-12-31&source_department=Цех-1&status=accepted
```
Параметры опциональны. Сейчас клиент загружает **все** партии и фильтрует локально — так нельзя при большом объёме данных.

#### 4.2. Права на аналитику
| Endpoint | operator | chief | ecologist | admin |
|----------|:--------:|:-----:|:---------:|:-----:|
| `/reporting/dashboard` | нет (403) | да | да | да |
| `/reporting/summary/by-hazard` | нет (403) | да | да | да |

Экспорт Excel/Word выполняет **клиент** (файлы на ПК), данные берёт с API.
